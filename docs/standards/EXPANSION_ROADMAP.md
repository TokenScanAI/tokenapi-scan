## 二、三步扩展路线（每步一个质检门槛）

### 阶段 0：地基固化（先做，零外部依赖）

| 任务 | 质检门槛 | 状态 |
|---|---|---|
| model_type 分类落库 | classify_model_type.py 全量跑通，非chat 35 个单独标注 | ✅ **已完成 10/4** — migration `20261004_0008` 已应用，5676 行全部落库（chat 5001 / video 197 / embedding 189 / audio 130 / image 104 / rerank 45 / invalid 10）。**门槛至此才第一次可执行**：该字段此前只存在于脚本打印输出里，DB 里从来没有过这一列 |
| chat-unknown vendor 补全 | resolve_vendor.py 导 CSV，**抽检 10 条对照 HF/官方文档全对**后落库 | 脚本就绪，待抽检（vendor=unknown 现为 2672 / 5676） |
| 非chat 模型移出对话主榜 | 主榜 SQL 加 `WHERE model_type='chat'` 过滤 | 待改 —— 字段已就位（440 个非chat canonical 有价格，过滤会影响它们），改前需先确认这些模型的独立子库去向 |
| 2 个脏数据清理（accounts/.../、fare-20b） | 人工确认后删 | 待删（accounts/fireworks/models/ 现判 invalid，仍在库） |

**门槛**：阶段 0 不通过（vendor 抽检不全对、非chat 未移出主榜），不进阶段 1。

> **10/4 顺带修掉的分类器 bug**：原判据是 `len(canonical_id) < 3` → `invalid`，
> 会把 `o1` / `o3`（OpenAI 推理主力，各 40 / 39 条价格行）误杀 —— 若照此执行
> "非chat 移出主榜"会直接削掉 79 条主力价格。改用 `MODEL_DATA_STANDARD §2.1` 的
> 客观依据：**vendor 非空即证明模型真实存在**（vendor 只从 HF 官方 org / 官方文档填充，
> 猜不到才标 unknown），因此不得因 ID 短而判脏。回归防护在 `tests/test_model_type.py`。

> **机制而非约定**（本条是本项目的铁律）：`model_type` 的判定只存在于
> `scripts/align/classify_model_type.py` 一处。`--write` 落库、`--check` 校验漂移，
> 两者都已挂进每日哨兵（`verify_v2_health.sh` 第 5g 项）。**禁止**在其他脚本或 SQL 里
> 另写一套判据回填 —— 规范里写一句"记得分类"而不挂检查，等于没写：不跑不失败，
> 漂移只会以"要不要改"的形式在几个月后路由到人前。

### 阶段 1：存量价格恢复（用第2步指纹库，不引新站）

| 任务 | 质检门槛 |

**门槛**：抽检偏差 >10% 的站点单独复核，不批量入库。

## 三、抽检校验门槛（贯穿所有阶段，铁律）

任何批量落库前强制：
1. 随机抽 5-10 条对照权威源（HF/魔搭/厂商官方/官方价）人工确认
2. 价格类对照官方锚模型，公式偏差 ≤10%
3. 防作弊：抽检是否混入标记性作弊数据 / 混淆 ID（用户明确要求）
4. 本地备份 DB（禁 git checkout），再写
5. 记 normalize_run，留可追溯日志

## 四、执行节奏（用户偏好：每天小步）

- 不一次性把 3 个阶段全做完。建议：阶段 0 一天、阶段 1 分 2-3 天（每天恢复 2-3 站抽检），阶段 2 单独评估。
- 所有抓取/定时通知统一到微信；健康监控 ≥30 分钟间隔避免限流。
- 每步产出落 CSV + 报告，用户抽检确认后再落库——**标准是"先看清单再拍板"，禁抢跑直接改生产 DB。**
